# History service audit and fixes

**Scope:** US-23 (list my past encounters) and US-24 (read an encounter snapshot), including the gateway, PostgreSQL read path, encounter writer, and browser history panel. The review assumed a single Compose deployment and players who accumulate more than one page of encounters. The read-only History service fits the project: Encounters owns the writes, and History can display stored results without consulting live teams or duplicating game rules.

## Findings and changes

| # | Finding | Change and verification |
| --- | --- | --- |
| 1 | **Older rows were unreachable from the list.** The response stopped at 50 by default (at most 200), with no cursor. Sorting only by `created_at` also left ties unspecified; PostgreSQL can give rows in one transaction the same timestamp. | [`History`](../services/history/app.py) now supports `before` and returns a relative `Link: …; rel="next"` when more rows exist. [`db-manager`](../services/db_manager/app.py) orders by `created_at DESC, id DESC` and uses the cursor's position in that order. The response body is still a JSON array. A live test pages through tied timestamps while a newer entry is added. |
| 2 | **One malformed snapshot could break the entire page.** The summary assumed `details`, nested monster fields, and team members had specific JSON types, but the storage type does not enforce that shape. | Summary generation tolerates missing and malformed fields: absent names are `null` or omitted from the team-name list. Valid detail objects are returned unchanged; a non-object snapshot is represented as `{}`. Unit tests cover mixed valid and malformed rows. |
| 3 | **Detail ownership was checked after the snapshot crossed the persistence boundary.** The original route already denied non-owners; this was not a confirmed public disclosure. Oversized IDs on the direct route could also become an upstream error rather than a `404`. | Detail now queries by both encounter ID and the verified player's ID. A caller cannot use another player's entry as a page cursor; foreign or unknown cursors return an empty page. IDs outside the database's positive `bigint` range are rejected before persistence. The new list query requires both the History service identity and its existing encounter-read ACL. Live tests verify owner access, non-owner `404`, cursor scoping, and that the detail survives deletion of the team. |
| 4 | **The browser had no way to reach older pages and could show stale history when changing accounts.** The panel retained its contents until a fetch completed, and a pending old request could overwrite the display. | [`frontend`](../frontend/app.js) adds **Older** and **Newest** controls. History is cleared on login/logout, and stale responses cannot render into another session. The gateway forwards only History's pagination header for this route and exposes it to the browser. Node tests cover the account switch and preserve cursor IDs as strings, avoiding JavaScript integer rounding. |
| 5 | **The History OpenAPI path was missing its required ID parameter, and the ordering regression test compared date strings.** HTTP dates are not lexically sortable across different weekdays. | Updated the [History](openapi/history.yaml), [gateway](openapi/gateway.yaml), and [db-manager](openapi/db-manager.yaml) specifications and the US-23 acceptance criteria. The live ordering test now parses dates before comparing them. The existing `created_at` wire format is unchanged. |

## Verification and deployment

- **111 Python unit tests, 2 frontend tests, and 22 targeted live integration tests passed.** Ruff, Bandit, Compose validation, OpenAPI YAML parsing, and `git diff --check` also passed.
- The scout ran on the registered `deepseek/deepseek-flash` model and reviewed the in-progress changes. Its recommendations led to explicit SQL parameter typing, application of the shared read ACL, and the timestamp-test correction. The final query was exercised against live PostgreSQL.
- **No schema migration is required for this History change.** Deploy the updated gateway, History, and db-manager together; rebuild the standalone frontend to expose the new controls.
- Not checked: full live suite, browser end-to-end behavior, performance under sustained History traffic, or snapshots on a deployed volume. List reads still transfer bounded snapshot JSON internally; no new index or rate limit was added. The API does not provide a fixed snapshot across page requests: newer entries appear on refresh rather than being mixed into older pages.
